orlog vs Mem0 — benchmark dashboard

A same-inputs, real-API benchmark of orlog against Mem0 on speed, accuracy, and abstention behavior. The headline accuracy numbers are nearly tied — that hides the real story, which is below.

The nuance the headline number hides

Overall accuracy

72.5% (orlog) vs 75.0% (Mem0) — near tie

A single blended score across 40 questions makes the two systems look almost identical. They get there in very different ways — see the next three cards.

Post-update accuracy

orlog 90% vs Mem0 0%

On the 10 questions about facts that were later updated, Mem0 answered every single one with the stale pre-update value in this benchmark's shared-bucket configuration — verified as a real behavior, not a grading bug. orlog got 9 of 10 right.

Abstention on unanswerable questions

orlog 46.7% vs Mem0 0%

orlog correctly says "I don't know" on close to half of genuinely unanswerable questions. Mem0 has no abstain concept — it always hands back its nearest-scoring memory, right or wrong, so it is never correct here.

Speed cuts both ways

Mem0 reads ~8x faster · orlog writes ~55x faster

Query p50: 203 ms (Mem0) vs 1,712 ms (orlog). Ingest p50: 31 ms (orlog) vs 1,680 ms (Mem0). Each system is faster at the opposite half of the workload.

Methodology

What was run

Both systems ingest the same 40 natural-language facts about 10 synthetic entities (plus 10 follow-up facts that update earlier ones), then answer the same 55 questions (40 about known facts, 15 about attributes never stored for that entity). Grading is a deterministic, case-insensitive substring match — not an LLM judge. All entities share one orlog event log and one Mem0 user bucket; neither system is told which entity a question is about.

Metrics shown here

  • Ingest / query latency — wall-clock per call, from 50 ingests and 55 queries (40 known + 15 unknown) per system.
  • Accuracy — overall (all 40 known-fact questions) and post-update-only (the 10 whose answer changed after a later update).
  • Abstention — on the 15 unknown-fact questions, orlog counts NO_CANDIDATES/other abstention as correct; Mem0 counts "nothing cleared its default similarity threshold" as correct.
  • Tokens — orlog's LLM call token counts; Mem0's client does not expose these, so it is shown as unavailable rather than zero.

Models

orlog runs on Anthropic's claude-haiku-4-5 (its own calibrated default); Mem0 runs on OpenAI's gpt-4o-mini. This ended up cross-provider rather than same-model — see the note below.

Model note: two real orlog bugs found and fixed while building this

The original plan ran both systems on the same OpenAI model for a strict same-model comparison. Building this benchmark surfaced two real, provider-independent problems, both fixed in src/orlog/ because they affect orlog generally, not just this benchmark:

  • gpt-5-mini incompatibility. It rejects any non-default temperature and the legacy max_tokens parameter, which both orlog's and Mem0's default extraction calls used — both runners were switched to gpt-4o-mini.
  • orlog's real-LLM derivation path failed on nearly every query, on every model tested, on both providers — including orlog's own README example. Root cause: the deriver received only a fact's bare stored value with no attribute label or grounding text, and the system prompt never told the model to restate the literal entity.attribute key that heimdall's SUPPORTS check requires. Fixed with two small, additive changes (an excerpt field already anticipated by the design spec, and a system-prompt instruction) — orlog's full test suite (283 tests) passes unchanged.

With both fixed, orlog ran on Anthropic (the provider that was actually available once this was diagnosed) rather than OpenAI for this final run. Full details, including why this is believed to be a genuine bug fix rather than a benchmark-side workaround, are in benchmarks/vs_mem0/README.md's "Model note" and docs/superpowers/specs/2026-07-17-vs-mem0-benchmark-design.md's "Known deviations" section.
